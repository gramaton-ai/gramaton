# Retrieval

## Primary Query Pattern: Filter → Rank → Traverse

The core of Gramaton's retrieval engine. A single operation that combines three capabilities no existing embeddable engine provides together:

1. **Filter** — Narrow candidates by metadata properties (`temporality = 'durable' AND confidence > 0.7`)
2. **Rank** — Within the filtered set, rank by vector similarity to the query
3. **Traverse** — From top-ranked results, follow relationship edges to discover connected knowledge

This maps directly to how an agent uses a knowledge store: "Find me high-confidence, durable knowledge about retry strategies, and show me what's related."

## The Retrieval Funnel

Enforced by API shape, not prompt instructions. Deeper tools require record IDs that can only be obtained from narrower tools first. LLMs cannot skip to expensive reads.

### Tier 1: Discovery (cheap, broad)

```bash
gramaton search "retry strategies" \
  --confidence-min 0.6 \
  --temporality durable \
  --knowledge-type semantic \
  --top 10
```

Returns lightweight results with both raw metadata and an LLM-readable summary:
```json
[
  {
    "id": "abc-123",
    "keywords": ["retry", "backoff", "jitter", "exponential"],
    "summary_short": "Exponential backoff with jitter outperforms fixed intervals...",
    "metadata_summary": "Current. Durable, high-confidence (0.85), well-established. Last accessed 19 days ago.",
    "confidence": 0.85,
    "temporality": "durable",
    "knowledge_type": "semantic",
    "epistemic_status": "well_established",
    "valid_from": "2026-02-10T00:00:00Z",
    "valid_until": null,
    "effective_score": 0.78,
    "last_accessed": "2026-03-15T10:00:00Z"
  }
]
```

Each result includes:
- **Raw metadata fields** — for CLI flag filtering and programmatic use
- **`metadata_summary`** — a one-line natural language interpretation generated by the tool layer. This is what the agent reads for a quick trustworthiness assessment.
- **`effective_score`** — the computed retrieval score after applying decay, importance, and similarity. Not shown to users — used by the agent for ranking.

Low token cost. Agent scans results and decides which are worth reading in depth.

### Tier 2: Inspection (medium cost)

```bash
gramaton inspect abc-123
```

Returns full content, all metadata, and one-hop related nodes as summaries:
```json
{
  "id": "abc-123",
  "content_full": "Exponential backoff with jitter...",
  "metadata_summary": "Durable, high-confidence (0.85), well-established. Created 2026-02-10. Last accessed 19 days ago. 3 related records.",
  "temporality": "durable",
  "confidence": 0.85,
  "epistemic_status": "well_established",
  "created_at": "2026-02-10T14:30:00Z",
  "related": [
    {"id": "def-456", "edge_type": "justifies", "summary_short": "API gateway timeout at 30s..."},
    {"id": "ghi-789", "edge_type": "related_to", "summary_short": "Circuit breaker pattern..."}
  ]
}
```

### Tier 3: Exploration (graph traversal)

```bash
gramaton explore abc-123 --depth 2 --edge-types "justifies,related_to"
```

Returns a subgraph fragment — multiple hops of connected knowledge:
```json
{
  "nodes": [
    {"id": "abc-123", "keywords": [...], "summary_short": "..."},
    {"id": "def-456", "keywords": [...], "summary_short": "..."},
    {"id": "jkl-012", "keywords": [...], "summary_short": "..."}
  ],
  "edges": [
    {"source": "abc-123", "target": "def-456", "type": "justifies", "weight": 0.9},
    {"source": "def-456", "target": "jkl-012", "type": "related_to", "weight": 0.7}
  ]
}
```

### Tier 4: Raw Access (expensive)

```bash
gramaton raw abc-123
```

Returns the original unprocessed source material from the source store filesystem.

### Delete and Purge (Repair Tools)

Repair tools, not knowledge management tools. Normal practice: supersede, not delete (tenet 8). See [Data Integrity — Repair Tools](data-integrity.md#repair-tools-delete-and-purge) for full details.

```bash
gramaton delete <id> [<id2> ...] --reason "description"   # soft — recoverable via rollback
gramaton purge <id> --reason "description"                  # hard — rewrites history, unrecoverable
```

Both require `--reason`. Purge requires interactive confirmation. Not included in agent integration kit.

### Ingest Command

Direct ingestion of text files from disk. No agent involvement — useful for bulk loading existing documents and seeding a knowledge base from a codebase or documentation set.

```bash
# Ingest a single text/markdown file
gramaton ingest ./architecture.md

# Ingest multiple files (shell glob)
gramaton ingest ./docs/*.md

# Ingest with a commit message (all files in one commit)
gramaton ingest ./docs/*.md --commit-message "Ingested service-a documentation"

# Ingest a directory recursively
gramaton ingest --recursive ./repos/service-a/docs/
```

What `ingest` does per file:
- Reads the file content as `content_full`
- Sets `source_ref` to the file path
- Extracts basic keywords via heuristic (not LLM) — headings, frequent terms
- Generates naive summary: first ~200 characters as `content_short`
- Generates embeddings via configured provider
- Chunks if content exceeds threshold
- Sets `processing_status: captured` — full LLM classification via piggyback curation later

**Batch behavior:** Multiple files in one `ingest` command are batched into a single commit. This matters for bulk loading — ingesting 300 files creates 1 commit, not 300. Rollback reverts the entire batch atomically.

**Embedding batching:** During bulk ingest, embedding calls are batched — multiple texts sent to the provider in one request where the provider supports it (Ollama and OpenAI-compatible APIs support batch embedding). This reduces overhead from per-request latency.

**Binary files are rejected:** `.docx`, `.pdf`, `.xlsx`, etc. return an error with guidance: "Convert to text first, or use your agent to extract text and capture via `gramaton capture`." Gramaton stores text — format conversion is the agent's job.

**Supported:** `.md`, `.txt`, `.json`, `.yaml`, `.csv`, `.html`, `.xml`, and other plain text formats.

### Bulk Ingestion at Scale

For large-scale ingestion (hundreds of repos, thousands of documents), considerations:

**Commit strategy:** Use `--commit-message` to group related files into logical commits. One commit per repo or per directory, not per file.

```bash
# Ingest each repo's docs as a separate commit
for repo in ./repos/*/; do
  gramaton ingest --recursive "$repo/docs/" \
    --commit-message "Ingested $(basename $repo) documentation"
done
```

**Embedding throughput:** At ~10ms per embedding via Ollama with batching, 30,000 records × 4 embedding levels = 120,000 embeddings ≈ 20 minutes. For larger ingestions, configure a faster embedding provider (API-based providers parallelize server-side) or run overnight.

**Progress reporting:** During bulk ingest, `gramaton status` shows progress:
```json
{
  "ingest_in_progress": true,
  "files_processed": 847,
  "files_total": 2300,
  "embeddings_generated": 3388,
  "elapsed": "4m12s"
}
```

```yaml
limits:
  max_content_length: 1048576    # 1MB per record
  max_keywords: 100
  max_summary_short: 500         # characters
  max_summary_abstract: 5000     # characters
```

## Versioning Tools

Gramaton's versioned property graph enables retrieval patterns that traditional vector databases cannot support. Every mutation creates a commit. The full history is queryable.

### Knowledge Diffing

Understand what changed over a time period or between two points in the store's history. This is a fundamentally different query from "what exists" — it answers "what evolved."

```bash
# What changed about authentication since March?
gramaton diff --since 2026-03-01 --topic "authentication"

# Everything that changed since March (no topic filter)
gramaton diff --since 2026-03-01

# What changed between two specific commits?
gramaton diff abc123..def456

# What changed on a branch vs main?
gramaton diff main..curation-2026-04-03

# Branch diff filtered by topic
gramaton diff main..curation-2026-04-03 --topic "caching"
```

**How `--topic` works:** The diff is computed in two steps:

1. **Structural diff (cheap).** Compare commits and produce the full set of changed records: added, modified, deleted. This is a hash comparison — fast regardless of store size.

2. **Semantic filter (only if `--topic` specified).** Run the topic string against the changed records using both keyword match (`content_keywords`) and embedding similarity. Records that match the topic are included; the rest are filtered out. This catches both exact keyword hits ("authentication") and related concepts ("OAuth2", "JWT", "login flow").

Without `--topic`, the full unfiltered diff is returned.

Returns a structured change set:
```json
{
  "topic_filter": "authentication",
  "time_range": {"from": "2026-03-01", "to": "now"},
  "added": [
    {"id": "rec-901", "summary_short": "Migrated session tokens to JWT", "confidence": 0.9}
  ],
  "modified": [
    {"id": "rec-234", "field": "confidence", "from": 0.9, "to": 0.4,
     "reason": "contradicted by rec-901"}
  ],
  "superseded": [
    {"id": "rec-567", "superseded_by": "rec-901", "summary_short": "Redis session store config"}
  ],
  "new_concepts": [
    {"id": "con-88", "name": "JWT rotation policy"}
  ],
  "new_edges": 8
}
```

**Agent use case:** "Catch me up on what changed while I was on vacation." The agent diffs the time range and narrates the changes. Turns "search for recent stuff" into "understand what evolved."

### Commit Audit Trail

Every record has a queryable history of how it arrived and how it changed.

```bash

```

Returns:
```json
{
  "record_id": "abc-123",
  "history": [
    {"commit": "f8a", "timestamp": "2026-02-10T14:30:00Z", "action": "created",
     "agent": "capture-subagent", "message": "captured from design discussion"},
    {"commit": "d2c", "timestamp": "2026-03-15T09:00:00Z", "action": "modified",
     "changes": {"confidence": {"from": 0.9, "to": 0.4}},
     "message": "contradicted by rec-456 — team migrated to Memcached"},
    {"commit": "91b", "timestamp": "2026-03-20T11:00:00Z", "action": "linked",
     "edge": {"target": "con-12", "type": "discusses"},
     "message": "linked to concept 'caching strategy' by curation"}
  ]
}
```

**Agent use case:** When a record has low confidence or contested status, the agent checks its history to understand WHY, then explains to the user: "This used to be our caching strategy but was superseded in March when the team migrated to Memcached."

### Branching

Named branches enable speculative reasoning and safe curation.

```bash
gramaton branch create <name>          # Create a new branch from current main
gramaton branch list                   # List all branches
gramaton branch merge <name>           # Merge branch into main
gramaton branch discard <name>         # Discard branch and all its changes

# Operations on a specific branch
gramaton capture --branch <name> --content "..."
gramaton search --branch <name> "query"
gramaton diff main..<name>             # See what the branch changed
```

**Speculative reasoning:** Agent explores a design option on a branch. Captures pros, cons, constraints without polluting the main store. If the option is adopted, merge. If rejected, discard. Maps to the neuroscience dual-store model — hippocampus holds things temporarily while evaluating, only consolidating what survives.

**Curation safety:** Piggyback curation runs on a branch. The curation subagent diffs the branch, reviews changes, and only merges what looks correct. Bad curation is discarded, not undone.

**Per-project isolation:** A security review, a spike, or an experimental project can have its own branch. Findings merge to main when the work is complete.

### Merge Conflict Resolution

When merging a branch, both sides may have changed the same node. Gramaton handles this automatically in v0.1.

**Non-conflicting changes (common case):** Auto-merge. New nodes on main + modified nodes on the branch = apply both.

**Property conflicts (both sides changed the same property):** Most recent timestamp wins. The losing change is preserved in the branch's commit history — nothing is lost.

**Duplicate concept nodes (both sides promoted the same keyword):** Detected via keyword/name match. One is kept, edges from the other are redirected. Logged in the merge commit.

**Node modified on one side, deleted on other:** Keep the node (tenet 8: never delete). Apply the modifications. Log the attempted deletion.

All conflict resolutions are recorded in the merge commit. `gramaton log` shows what was auto-resolved and how.

```yaml
merge:
  conflict_strategy: timestamp_wins
```

Interactive three-way merge with manual conflict resolution is a future feature. For v0.1, auto-resolution is sufficient — curation branches are short-lived (created and merged within one session), so conflicts are rare and low-stakes.

### Rollback

Atomic revert of any commit.

```bash
gramaton log --last 10                 # See recent commits
gramaton revert <commit>               # Revert a specific commit
```

**Agent use case:** "That batch of records I just captured from the vendor doc was wrong — they sent an outdated version." One command reverts the entire batch cleanly.

### Export / Import

Gramaton's default is one store containing all knowledge — the value is in cross-domain connections. But subsets can be exported as portable archives for sharing, backup, or seeding other stores.

```bash
# Full export (default — everything)
gramaton export --output my-knowledge.gramaton

# Export a specific node and all its children/edges recursively
gramaton export --node <id> --recursive --output kafka-decision.gramaton

# Export filtered by topic (keyword + embedding match)
gramaton export --topic "event pipeline" --output event-pipeline.gramaton

# Export a branch
gramaton export --branch security-review --output security-review.gramaton

# Export a time range
gramaton export --since 2026-03-01 --output q1-knowledge.gramaton

# Combine filters
gramaton export --topic "authentication" --since 2026-01-01 --output auth-q1.gramaton

# Import into another store (deduplicates by content hash)
gramaton import event-pipeline.gramaton
```

The export archive contains a subset of content-addressed chunks (nodes, edges, commits). Import is additive — imported records keep their IDs and edges. Duplicate detection via content hash prevents re-importing existing records.

**Use cases:**
- Share project-specific knowledge with a teammate
- Back up the full store or a subset to a portable file
- Seed a new store with relevant knowledge from an existing one
- Migrate knowledge when changing machines

**Multi-store note:** The default and recommended setup is one store per user (`~/.gramaton/data/`). A `--data-dir` flag exists as an escape hatch for users who genuinely need isolated stores. But the graph is designed to handle multi-domain knowledge — metadata, keywords, concept nodes, and edges provide the organization. Splitting into separate stores loses cross-domain connections.

## Scoring Model

This is the single authoritative definition of how retrieval scoring works. All scoring is computed at query time — no scoring values are stored.

### Two Time Signals

Retrieval scoring uses two independent time signals with different curves:

**Access recency** — "How long since someone found this useful?" Exponential decay. Fast. Each access resets the clock. This handles the day-to-day signal: frequently used knowledge stays accessible.

**Knowledge freshness** — "How old is the underlying knowledge in the world?" Power law decay. Gentle, long tail. A 2021 strategy doc ranks below a 2025 one, but neither goes to zero. This handles the case where multiple records about the same topic were created at different real-world times.

For records with `valid_from` and `valid_until` set (documents with known dates, decisions with clear timelines), hard filtering is preferred over soft scoring — see "Validity Filtering" below.

### Validity Filtering (Before Scoring)

Before scoring, the search tool applies validity filtering:

- **Default behavior:** Records where `valid_until` is null or in the future are preferred. Records with `valid_until` in the past are included but ranked lower (a penalty multiplier, not exclusion).
- **`--include-historical`:** Treats all records equally regardless of `valid_until`. For queries about evolution, history, or "what changed."
- **`--valid-from-range 2021-01-01..2021-12-31`:** Hard filter to a specific time window.

This means: five strategy docs from 2021-2025 all ingested today, the 2025 doc (no `valid_until`) ranks at the top by default. The agent sees "Current" vs "Historical" in the metadata summary and knows which to trust.

### Stored inputs (updated by events)

| Property | Updated when | What it represents |
|----------|-------------|-------------------|
| `access_count` | Record returned to a consumer | How frequently this record is used |
| `last_accessed` | Record returned to a consumer | How recently this record was used |
| `activation_boost` | Neighbor of an accessed record | Indirect activation from nearby frequently-used records |
| `confidence` | At capture or by curation | How likely this record is correct |
| `importance` | At capture or by curation | Retrieval priority floor — protects high-importance records from decay |
| `temporality` | At capture or by curation | Selects which decay rate applies |
| `valid_from` | At capture | When this knowledge became true in the world |
| `valid_until` | At capture or by curation | When this knowledge stopped being current |

### Computed at query time (never stored)

```
# Step 1: Validity filtering
# Records with valid_until in the past get a penalty (default: 0.5 multiplier)
# unless --include-historical is set
validity_multiplier = 1.0 if (valid_until is null OR valid_until > now OR include_historical)
                      else 0.5

# Step 2: Scoring
effective_score = validity_multiplier × (
    weight_similarity  × similarity +
    weight_recency     × access_recency +
    weight_freshness   × knowledge_freshness +
    weight_frequency   × frequency_score +
    weight_activation  × activation_score +
    weight_confidence  × confidence
)

# Step 3: Importance floor
if importance > importance_threshold:
    effective_score = max(effective_score, importance × importance_floor_ratio)
```

Where:

```
similarity         = cosine similarity between query embedding and record embedding
                     (0.0-1.0, from the vector index)

access_recency     = e^(-decay_rate[temporality] × hours_since_last_access)
                     (exponential decay — rewards recent use, resets on access)

knowledge_freshness = 1 / (1 + hours_since_knowledge_time / freshness_scale) ^ freshness_exponent[temporality]
                      (power law — gentle decay, long tail, old knowledge stays visible)
                      where: knowledge_time = valid_from if set, otherwise created_at

frequency_score    = log(1 + access_count) / log(1 + max_access_count)
                     (normalized to 0.0-1.0 across the store)

activation_score   = activation_boost × e^(-activation_decay_rate × hours_since_boost)
                     (activation_boost decays independently)
```

### Access decay rates by temporality (exponential)

Research-informed defaults based on Ebbinghaus forgetting curves and Generative Agents (Park et al. 2023). The formula `e^(-rate × hours)` gives a half-life of `0.693 / rate` hours.

| Temporality | decay_rate | Half-life | After 1 day | After 1 week | After 1 month |
|---|---|---|---|---|---|
| `ephemeral` | 0.173 | 4 hours | 0.016 | ~0 | ~0 |
| `temporal` | 0.0096 | 3 days | 0.79 | 0.19 | 0.001 |
| `durable` | 0.000321 | 90 days | 0.99 | 0.95 | 0.79 |
| `immutable` | 0.0 | ∞ | 1.0 | 1.0 | 1.0 |

### Knowledge freshness by temporality (power law)

The formula `1 / (1 + hours / scale)^exponent` decays quickly at first but has a long tail — old knowledge doesn't go to zero. This matches Bahrick's "permastore" finding that meaningful, well-learned material reaches a stable floor.

| Temporality | Exponent | 6 months | 2 years | 5 years | 10 years |
|---|---|---|---|---|---|
| `immutable` | 0 (freshness = 1.0 always) | 1.0 | 1.0 | 1.0 | 1.0 |
| `durable` | 0.5 | 0.82 | 0.56 | 0.43 | 0.32 |
| `temporal` | 1.0 | 0.67 | 0.33 | 0.18 | 0.10 |
| `ephemeral` | 1.0 | 0.67 | 0.33 | 0.18 | 0.10 |

`freshness_scale` = 8760 hours (1 year).

**Immutable:** Freshness is always 1.0. A mathematical proof from 1684 is as fresh as one from 2024. Age is irrelevant for definitional truths.

**Durable (exponent 0.5):** Five strategy docs from 2021-2025 rank clearly (0.82 → 0.43) but none are invisible. The 2025 doc is ~2x the 2021 doc. Gentle enough that a 10-year-old durable record still scores 0.32.

**Temporal/Ephemeral (exponent 1.0):** Steeper. A 2-year-old temporal record is at 0.33. Access decay (exponential) is the primary driver for these — the power law freshness is a secondary signal.

```yaml

  scale: 8760
  exponents:
    immutable: 0
    durable: 0.5

  attenuation_factor: 0.5
  decay_rate: 0.05
```

All values are starting points to be tuned during validation. The formulas and structure are design decisions. The specific constants are empirical.

## Spreading Activation

When a node is returned to a consumer (any retrieval that includes the node's content):

1. **Direct access:** `node.access_count += 1`, `node.last_accessed = now`
2. **Neighbor activation:** For each edge from the accessed node to a neighbor:
   `neighbor.activation_boost += base_amount × edge.weight × attenuation_factor`
3. **Single-hop only.** No multi-hop propagation — attenuates too fast to matter, expensive, hard to control.

The `activation_boost` on a neighbor accumulates from multiple activations (if it's near several frequently accessed nodes) and decays over time via `activation_decay_rate`. This keeps knowledge adjacent to frequently-used knowledge accessible, even if it hasn't been directly accessed recently.

**Concurrency note:** The direct access writes (`access_count`, `last_accessed`) and neighbor activation writes (`activation_boost`) are triggered by reads. Under concurrent agent load, these writes are serialized by the server. If this becomes a bottleneck, activation writes can be batched (accumulated in memory, flushed periodically) without affecting correctness — activation is approximate by nature.

## How Agents Use Retrieval

Retrieval is **transparent** — the agent searches Gramaton as part of its normal reasoning, not because the user asked it to.

The agent's system prompt instructs it to search before answering questions about past decisions, project context, user preferences, or domain knowledge. The search happens inline (synchronous) because the agent needs results before responding.

```
User: "How should we handle retry logic for our API?"

Agent thinking:
  → "User is asking about retry logic. I should check Gramaton."
  → gramaton search "retry logic API" --confidence-min 0.5 --top 5
  ← [results with keywords, short summaries, confidence scores]
  → "Record abc-123 looks relevant. Let me get the full content."
  → gramaton inspect abc-123
  ← [full content + metadata + related records]
  → Uses this to inform response

Agent response:
  "Based on the architecture decision from February, we're using
   exponential backoff with jitter. The constraint was the 30s 
   API gateway timeout. Here's how to apply that to..."
```

The user never typed a command. The agent autonomously decided to search, found relevant knowledge, and used it.
